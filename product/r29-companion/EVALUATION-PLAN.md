# Does S-Class find and fix errors better than blind prompting? — evaluation plan (master Ch.9 + §1.9 "sloppy-agent suite, false-completion rate")
Status: design only. No result exists. Nothing here is evidence until the runs below are executed and reviewed. Method follows public benchmark practice (SWE-bench-style tasks scored by hidden tests, seeded-defect/mutation testing, controlled A/B with identical model). I make no claim about how any specific company evaluates internally.

## 1. Hypotheses (stated before running, so they can fail)
H1 With the same model and tasks, S-Class lowers FALSE COMPLETION (agent says done, hidden tests/acceptance fail) versus plain prompting.
H2 S-Class does not cause an unacceptable rise in FALSE BLOCKS (valid work refused) or developer interruptions or cost.
H3 S-Class catches more SEEDED DEFECTS before declaring completion.
H4 Repairs under S-Class converge within the retry budget more often than unguided retries.
If H1 or H2 fails, the design needs changing, not the metric.

## 2. Arms (same model, same tasks, same repo snapshots, same time/token cap)
A. Plain agent (blind prompting): task text only.
B. Strong prompt agent: task text + a well-written checklist prompt ("write tests, run them, don't claim done without evidence"). This is the honest baseline: S-Class must beat good prompting, not a strawman.
C. S-Class full (gates + evidence + scope authorisation).
D. S-Class ablations: no independence rule; no scope boundary; no fresh-evidence rule (shows which controls earn their cost).

## 3. Task sets (two kinds)
T1 Real tasks: issues from open-source repos in each of Java, Python, JavaScript, TypeScript (pinned commit, existing test suite, hidden tests written/held out by someone other than the agent). Target >= 30 per language for the final run; pilot with 5 per language.
T2 Seeded-defect tasks: take passing repos, inject realistic bugs (mutation operators + hand-made logic/regression/security/off-by-one bugs, some in untested code), ask the agent to find/fix or to add a feature without breaking behaviour. Ground truth known exactly.
T3 Sloppy-agent suite (from §1.9): scripted bad-behaviour agents (claims success without running tests, edits outside scope, rewrites tests to pass, ignores a requirement, uses stale evidence). S-Class must block every scripted cheat; a plain agent harness will not. This is a unit-level proof of the controls, not of overall usefulness.

## 3b. Research-driven requirements (see RESEARCH-NOTES-R29.md A, B)
- Hidden-test scoring must use held-out AND strengthened tests (extra tests targeting code the patch touches, mutation-derived tests). Public work reports that tests visible in the benchmark overstate success (7.8% to 19.78% of passing patches rejected under stronger checking, depending on method); we report both the plain and the strengthened score.
- Add a hacking audit to every run: test-file/harness edit detection, a network/upstream-fix check, and an independent LLM-judge plus human spot check of flagged runs. Report hack rate per arm separately from correctness.
- Process data: log full trajectories so that a trajectory monitor can be evaluated later (OI-051); S-Class itself does not claim to monitor trajectories.
- Developer time and interruption cost are first-class outcomes (published RCT evidence that AI tools can slow experienced developers; RESEARCH-NOTES D).

## 4. Metrics (all with denominators and 95% confidence intervals; paired comparisons per task)
Primary: false-completion rate (claimed done AND hidden acceptance fails). Safety/utility: false-block rate (valid work refused, judged by an independent labeller), task success rate (hidden tests pass), seeded-defect detection rate before completion, scope-violation rate. Cost: tokens, wall time, number of developer interruptions/approvals, gate latency (compare to contract numbers measured on Linux CI, not Windows). Convergence: repairs within budget.
Labelling: outcomes labelled by hidden tests plus an independent human/second-model audit label recorded before looking at arm identity where possible.

## 5. Protocol rules
- Pre-register hypotheses, task list, metrics and stopping rule in governance/EVAL-PREREG.md before any run; no post-hoc task removal.
- Same model version, temperature and budget for all arms; N runs per task (>= 3) to measure variance.
- Models and IDE hosts recorded per run; results reported per (host x language) cell; a cell's QUALIFIED status requires its own results.
- Raw run logs kept; scoring script reviewed by CL; results table generated by script, not typed.
- Negative results are published in STATUS.md as they are.

## 6. What must exist first (dependencies on the roadmap)
Working gate + fixture runner (H3), one host adapter (H5 B11), the reference language pack, a harness that can drive arms A-D headlessly (B18). Pilot (T3 plus 5 tasks) possible right after the first vertical slice; full study at H6.

## 7. Decision use
Pilot result decides whether to continue the roadmap as designed, change a control, or cut a feature. Final result goes into the H7 release bundle as evidence for the thesis, with confidence intervals and limits (benchmark tasks are not the whole world).
